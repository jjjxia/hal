1. ZipCPU/dspfilters slowfil_srl
   Upstream 16d7dc3b23af167759693da9caff7c7111805873, rtl/slowfil_srl.v.
   LGPL-3.0-or-later RTL. Parameterized instance: LGNTAPS=3, NTAPS=7,
   IW=8, TW=8, OW=19, FIXED_TAPS=1. Seven signed taps 3,-5,7,11,-13,17,19;
   unused eighth coefficient zero. This is an explicitly configured upstream
   design, not the original 110-tap default or a new hand-built FIR.
   Coefficients become hardware ROM contents at synthesis, never recovery hints.
   Reset does not clear sample storage. Preserve a documented zero-sample flush
   prefix, then one sample every 16 clocks. Exact 7-tap signed integer sum is the
   evaluation reference; validate its alignment against upstream RTL first.
   Test: shared multiply/accumulate and delayed sample dependencies. A passing
   whole-state replay alone does not count as recognizing a FIR algorithm.

2. ZipCPU/cordic seqcordic
   Upstream 8ede08a1865d87a357a3a2c188206e843dd9bde6, rtl/seqcordic.v.
   LGPL-3.0-or-later RTL, unchanged checked-in widths IW/OW=13, WW=16, PW=20.
   Reset four rising edges, then start one transaction every 17 edges.
   Vary all octants, boundaries, signed inputs, auxiliary bit, then seeded random
   held-out tuples. Actual RTL outputs include rotations 1..14; preserve its
   NBA timing rather than substituting ideal trig or the pipelined architecture.
   Test: fixed iteration schedule with data-dependent sign/add/subtract guards,
   shared x/y/phase state, shift position and rounding. No new recognizer rule or
   hand-supplied CORDIC name/recurrence goes into recovery.

Post-run diagnosis: core contract versus implementation completeness
   InvFold's periodic-equation contract permits data-dependent arithmetic/selects
   inside an expression; it requires periodic effective writes and expressions,
   not periodic data values (NetNotary sections/inverse.tex:13-28). The CORDIC
   exclusion therefore does not establish an inherent inability to represent
   its branches. Current guided.cpp specializes primitive-control values, then
   folding.cpp requires repeating specialized expressions. Investigate retaining
   symbolic data guards with checked equations as a generic frontend correction.
   Whether this yields a useful complete graph still needs a separate test.

   The native C++ arithmetic model currently fits dyadic affine/floor functions;
   it is not a general multiplier/variable-shift/conditional-operation recognizer.
   The old invfold/identify.py contains filter sections/transfer functions and
   FIR/IIR classification, but the new native analyze CLI does not invoke or
   implement that section-recognition layer. Porting/integrating it is unfinished
   generic engineering, and cannot by itself repair missing word order or make
   CORDIC a linear filter. Do not describe the C++ migration as completion of
   every high-level capability of the earlier exploratory recognizer.
   Keep three outcomes separate: anonymous word recovery, exact event graph,
   readable/identified algorithm. No per-design names, order hints or hand-coded
   FIR/CORDIC recurrences are authorized as evidence of automatic recovery.
